# SceneLex — 项目战略文档

> 最后更新：2026-07-16
> 基于 AGENT.md、README.md 与 一、先明确系统最终要解决什么问题.md 提炼

## 1. 产品愿景

构建一套**"场景即释义"的词义语义资源与教学证据系统**。核心主张：

> 可验证的词义边界 + 能证明学习迁移的场景证据。

SceneLex 不是某个学习 App 的内部素材目录，也不由某个词典、播放器、课程或模型厂商定义。它是一套可独立发布、版本化和复用的语言资源，供词典、课程、播放器、API、学习实验和研究工具等多个消费者复用。

## 2. 核心问题

传统学习路径是 `L2 声音 → L2 文字 → L1 翻译 → 概念`，学习者始终通过母语翻译中介理解 L2。SceneLex 要建立的是：

```text
L2 声音 → 场景与经验 → 概念
```

让学习者在什么样的经验、状态和关系中，人会自然使用某个表达 — 而不是记住它"翻译成什么"。

## 3. 核心原则

1. **词义，不是词头。** `run` 的不同含义是不同的教学单位。
2. **场景是释义媒介，不是装饰。** 目标词必须由场景中的经验、关系、动作或结果不可替代地支持。
3. **先经验与声音，后文字。** 先让学习者看见语义事件，再在恰当时机出现 L2 声音；文字和 L1 是辅助，不抢占默认意义通道。
4. **一个词义需要证据组。** 原型、对比、反例、边界、迁移是五种教学功能。
5. **语义骨架与具体渲染解耦。** 词义骨架描述语言共同体中的可检验假设，不绑定某个房间、职业或文化脚本。
6. **生成不等于发布。** LLM 可以起草，但内容必须通过语言、场景和教学三层审核。
7. **不把翻译绝对化或妖魔化。** L1 可用于澄清抽象概念，但不能替代声音—经验连接。
8. **相邻概念不必互斥。** 词义可能包含、重叠、程度差异或不同维度；排除条件只写真正不成立的情况。
9. **API 按协议适配。** 模型名、厂商、URL 和认证只能存在于适配层。

## 4. 权威边界

```text
word sense specification        ← Schema 权威
        ↓
semantic skeleton + conditions + L1 confusables
        ↓
teaching-scene evidence (model-neutral IR)
        ↓
renderer adapters (image / video / TTS / interactive)
        ↓
reviewed / published resources
        ↓
learning clients, APIs, content packages
```

- **SceneLex 拥有**：词义规格、场景证据规格、审核结论、资源版本。
- **SceneLex 不拥有**：学习者身份、学习记录、UI、渲染模型选择、HTTP 路由、个性化状态。

## 5. 内容状态与发布门

```text
candidate → draft → reviewed → published
```

三层发布门：

1. **schema-valid**：结构校验通过。
2. **reviewed**：语言、语义、场景与教学审核通过。
3. **published**：来源可追溯，学习任务可评分，迁移证据通过实验或有明确审核记录。

当前仓库内资源均为 `reviewed`，尚未宣称 `published`。

## 6. 产品原则

- **资源是核心，产品是消费者。** 学习产品消费资源完成教学，同时通过实验验证资源质量。
- **体验与功能优先，产品形态保持开放。** 阶段范围管理交付顺序，不冻结长期形态。
- **本地优先，厂商中立。** 内容生产可使用多个 LLM，但正式资源不绑定任何厂商。
- **规模化的前提不是 Schema 能通过。** 是资源在新场景中确实产生了可复现的学习迁移。

## 7. 非目标（当前阶段明确不做）

- 制作高成本影视级视频。
- 大规模词义库（数千义项）。
- 完整的自适应学习产品。
- 云同步、多用户、商业化。
- 绑定特定 LLM 厂商或渲染模型。
